# Pi Deck 0.7.x — Local Output Library: PR/FAQ and PRD

- **Status:** Proposed product contract for design review; not shipped or implementation-approved.
- **Date:** 2026-09-26
- **Target:** `0.7.x`
- **Repository baseline:** `75f54706fb73245887819905bbff5e3805899460`
- **Tracking issue:** [#141 — Local Output Library](https://github.com/LiusuZeng/pi-deck/issues/141).

This document starts with a working-backwards press release and FAQ, then defines normative product behavior. The press release describes the intended experience, not an announcement of released functionality. “Must” requirements in the PRD are the proposed acceptance contract; changing them requires an explicit product decision, not an implementation shortcut.

> **Current product boundary:** This proposal is distinct from the shipped manual text-deliverables Outputs MVP ([PR #177](https://github.com/LiusuZeng/pi-deck/pull/177)); see [Local Output Library — manual text-deliverables MVP](local-output-library-slice-0-design.md). The MVP supports user-initiated saving of completed assistant text, retrieval, review, and revision. It does not implement this proposal's managed publication, Automatic/Require output/Chat only policy, arbitrary multi-file packages, lifecycle/import actions, or workflow publication. Nothing in this document approves or validates those proposed capabilities.

## Decision summary

**Product promise:** Describe the deliverable once. Deck handles its local filing, indexing, and revision lifecycle—and reports whether it was actually saved. Any result Deck labels Saved is a durable local file package, not just a claim in chat.

The user-requested direction is:

- Indexed, structured, local-file-based outputs.
- First-class review and iteration.
- Easy retrieval and reuse across sessions.
- Framework-managed output conventions, without repeating storage/formatting instructions in every prompt.
- No Git requirement or coding-only dependency.

The proposed defaults below make that direction concrete. In particular, Automatic versus Require output, the initial format/size limits, review states, and release slices are product proposals for review, not claims that the user already specified these details.

# Part I — Working-backwards PR/FAQ

## 1. Draft press release

### Pi Deck introduces a local library for the work your agents produce

**Find the report, review the result, and request the next revision—without reconstructing a conversation or telling every agent where to save its work.**

Pi Deck's Local Output Library makes deliverables a first-class part of the desktop experience. Reports, plans, datasets, and other files are saved in a predictable local structure, indexed for retrieval, and linked to the work that produced them. Users can review a result, request changes, and keep its revisions together, even after its original session has been closed or deleted.

Agent conversations are good places to explore an idea, but poor filing systems. A useful answer may be buried between tool activity and follow-up questions. A generated file may live in a directory the user no longer remembers. Revising it in another session often means explaining the output conventions and context all over again.

With the Local Output Library, users describe the work rather than its filing procedure. Pi Deck supplies the output contract and destination, validates saved packages, records their origins, and updates a local search index. A result card in the conversation opens the saved output directly. The Outputs library retrieves results by their title, contents, workspace, type, tags, or date.

For example, a user asks for a comparison of three vendors. Deck saves a report and supporting table together. Later, the user finds the comparison through search, reviews revision 1, and asks for a version focused on a smaller budget. Deck supplies that revision as context and saves revision 2 without replacing revision 1. The user does not need the original chat to continue the work.

Outputs remain ordinary local files with readable metadata. They can be opened in other applications, copied, or backed up without Pi Deck. The search index is replaceable; the files are the durable record. Git, a cloud account, and a vector database service are not prerequisites.

Local storage and search do not require another model call. Generating or revising content still uses the user's configured Pi model and incurs its normal costs. Local storage does not prevent Pi from sending explicitly selected content to that provider.

## 2. Customer FAQ

### Q1. What is an output?

An output is a named deliverable with one or more files, structured metadata, revision history, and review information. A report and its supporting CSV can be one output. Two unrelated reports are separate outputs. A transcript, tool log, or progress message is not automatically an output.

### Q2. Do I need to keep prompting “save this to a file”?

No. Deck supplies the output instructions, authorized destination, and save operation. Automatic mode asks the agent to identify reusable deliverables during ordinary work. For guaranteed tracking of a requested deliverable, choose Require output once as a workspace preference or for a particular submission. This expresses intent in the product, not a repeated prompt template.

Automatic selection is model-assisted and can miss or over-identify a deliverable. The framework guarantees the integrity of a saved output, not perfect interpretation of every conversational request. Save as output remains available on a completed answer.

### Q3. Does every response become a file?

No. Clarifications, acknowledgments, status updates, thinking, and raw tool logs do not fill the library. Chat only disables agent publication for that work. Require output records an explicit expectation and shows an actionable incomplete state if no deliverable was saved.

### Q4. What does “structured” mean?

The package has a predictable identity, metadata, file inventory, provenance, and revisions. The content uses appropriate ordinary formats: Markdown for a report, CSV for a table, JSON for structured data, or another file type. Users do not have to convert every result into a proprietary format or JSON document.

### Q5. Where does my work live?

In one local library folder, configurable before first use, with a default under Pi Deck's local home. The UI exposes the folder through Reveal in Finder. Each output contains ordinary files and human-readable JSON metadata. This is separate from Pi's JSONL conversation history and independent of project working directories.

### Q6. How do I find something later?

Use All Outputs or workspace-scoped Outputs. Search titles, summaries, tags, file names, and the contents of supported text files. Filter by workspace, type, review status, and date. Results open the deliverable, not a transcript search result. Historical revisions remain available from that output.

### Q7. How do review and iteration work?

Review a specific saved revision, add notes, mark it Accepted, or request changes. Revise opens a draft session with that revision and the feedback attached. Sending starts the normal Pi work. The new revision becomes current and starts Unreviewed; the earlier revision and its review record remain available.

Accepted means the user accepted those bytes. It does not certify factual accuracy, imply passing tests, approve tool execution, or publish anything outside the machine.

### Q8. Must I resume the original session to revise a result?

No. An output has its own identity. Its source session is provenance, not its owner or lifetime. A new session can revise it using selected files and feedback without loading the original conversation. Source links may become unavailable without making the output unavailable.

### Q9. Can I use the files outside Deck?

Yes. Reveal, open in the operating system, and export a copy are supported. Exporting a copy is the recommended way to edit externally; it can be imported as a new revision. If a published file is changed directly, Deck reports the integrity change and does not silently treat it as the same accepted revision.

### Q10. What happens if I delete a chat or lose the search index?

Deleting a chat does not delete its outputs. The index can be rebuilt from output packages, including revision and review metadata. It cannot recreate output files the user has deleted or overwritten; ordinary filesystem backup is still necessary.

### Q11. Is this a Git manager, document editor, or agent memory system?

No. It is a local deliverable library and review loop. There is no Git dependency, mandatory branch management, full editor, automatic retrieval of unrelated private material, or promise of universal undo. Git-derived evidence and specialized previews may be added later without becoming prerequisites.

### Q12. Does it expose private Parallel task sessions?

No. Private task sessions remain private. Only a parent-authorized, user-facing result can become a library output. Their prompts, transcripts, internal paths, runtime IDs, and raw tool results do not become searchable artifacts.

### Q13. What does it cost me?

- Disk space for saved files and revisions; storage use is visible and cleanup is explicit.
- A small output-policy/tool-schema context overhead in supported Pi sessions.
- Normal model charges when generating or revising content. No extra reviewer or embedding call is mandatory.
- One-time output preference/folder configuration if the defaults are unsuitable.
- Occasional decisions when concurrent revisions conflict, files were edited externally, or a requested output was not saved.

No automatic retention deletion, cloud subscription, or continuous model-powered indexing is part of the first release.

### Q14. Is a local library private?

Deck does not upload or sync the library for indexing. Only explicitly bound outputs are provided to agent work; selecting an output is not permission to load the whole library. However, Pi workers and other local programs have their normal operating-system permissions, and selected content may be sent to a configured model provider. Workspace organization is not an OS sandbox or a multi-user security boundary. Deck cannot guarantee that user-produced files contain no secrets.

## 3. Internal FAQ

### Why should the framework own this?

Naming, destinations, identity, metadata validation, publication, indexing, revision retention, and retrieval are repeatable product mechanics. Having each session recreate them produces inconsistent paths, missing metadata, overwritten results, and prompt boilerplate. The agent should create content; Deck should manage its durable lifecycle.

### Why not just export the final answer or scan the project folder?

An export lacks stable output identity, versioned review, reuse bindings, and cross-session retrieval. A general folder scan cannot reliably distinguish intentional deliverables from source files, intermediate files, secrets, dependencies, or another agent's work. This product registers explicit output packages; it does not scrape every file the agent touches.

### Why not add a new task or orchestration system?

The repo already has sessions, Work, private Parallel tasks, and role-based workflows. Outputs add a durable result object alongside those systems, not another execution engine or persisted Work entity. Existing execution and navigation contracts remain intact.

### What is technically new, and what can be reused?

New: an output schema/store, file-publication boundary, revision/review model, rebuildable index, authorized runtime bridge, library UI, and revision-context binding.

Reusable: managed Pi extension launch, typed IPC, local JSON persistence patterns, workspace scope, ordinary session drafts, attachment/path safety patterns, and parent-mediated Parallel synthesis. Existing single-file atomic stores do not already solve multi-file publication.

### How expensive is the feature to build?

Treat the initial normal-session library as a medium-to-large feature project, not a diff viewer. The largest risks are publication/recovery, external mutations, safe file access, and source-independent iteration—not the list screen. The earlier Git/worktree effort estimate is superseded and does not apply to this PRD.

Size and schedule the slices in section 15 after a publication/recovery and revision-binding design spike. Do not commit a release date until those contracts and supported Pi-version requirements are demonstrated. Avoid spending the core budget on arbitrary previews, semantic search, or a new orchestrator.

### What would falsify the bet?

If users still search old conversations to find results, copy paths/context manually for revision, repeat save instructions, or cannot safely trust which revision they are viewing, the feature has not delivered its promise. More files on disk alone are not success.

# Part II — Product Requirements Document

## 4. Problem, audience, and goals

### Primary audience

A single local Pi Deck user producing reusable deliverables across sessions and workspaces: research, writing, planning, analysis, data preparation, and coding-related documents. Neither a source repository nor programming is required.

### Jobs to be done

1. “When an agent produces useful work, keep it in a predictable place without me becoming its filing clerk.”
2. “When I return later, find the result even if I have forgotten the session, filename, or folder.”
3. “When I give feedback, use the exact version I reviewed and preserve what came before.”
4. “When I continue in another session, reuse the result without replaying its whole conversation.”
5. “If I stop using Deck, retain understandable files rather than opaque application-only content.”

### Goals

- G1: Durable local outputs, independent of session and runtime lifetime.
- G2: Consistent structure supplied by Deck, not repeated user instructions.
- G3: Reliable retrieval across accessible workspaces.
- G4: Version-bound review, feedback, and revision.
- G5: Honest save, completeness, integrity, and indexing states.
- G6: Preserve Pi-native sessions and existing privacy/ownership boundaries.

### Non-goals for the initial library release

- Git/worktree management, source-change attribution, automatic merge or universal rollback.
- A source/document editor, collaborative document service, multi-user permissions, cloud sync, or hosted search.
- A replacement for Pi JSONL history, Work, Parallel planning, or Agent Workflows.
- Semantic/vector search, OCR, automatic web-source verification, or model-generated indexing summaries as a requirement.
- Ingesting all existing chats or scanning arbitrary project directories for candidate outputs.
- Automatic publication of every workflow occurrence or private worker artifact.
- Arbitrary archive import, executable document rendering, or specialized viewers for every file type.
- Git-like branching/merging of revisions or automatic merging of external edits.
- Automatic deletion of old revisions, multi-library federation, or automatic relocation of a nonempty library.

## 5. Product concepts and identity

| Concept | Definition / invariant |
| --- | --- |
| Output | One named deliverable, with an app-generated stable `outputId`, one owning workspace, metadata, files, revisions, and review records. |
| Revision | A durably committed file snapshot with its own stable `revisionId`, increasing display number, file inventory/checksums, source information, and optional base revision. |
| Current revision | The most recently committed revision of an output, regardless of review status. Opening a search result defaults to this revision. |
| Accepted revision | A specific revision explicitly accepted by the user. It need not be current; it must never silently stand in for a newer unreviewed revision. |
| Output attempt | A bounded save/revision operation with a host-assigned ID, source binding, expected base/head where applicable, and durable publication outcome. It is not a new schedulable Work entity. |
| Staging area | Non-public working files for an attempt. Not indexed, presented as saved, or treated as historical revisions. |
| Output reference | An explicit binding to `outputId + revisionId` and selected files, not a floating “latest” filename. |
| Provenance | Source session/workflow identifiers when available, generation/import origin, timestamps, and optional input-output references. Not a private transcript. |

**ID-1.** Output identity must not be a runtime ID, Pi session ID/file path, filename, title, cwd, project path, or Git revision. Source identifiers are provenance only.

**ID-2.** Each output belongs to exactly one workspace. Global creation uses the existing persisted default workspace; a named workspace is not required. Workspace membership is independent of physical library paths.

**ID-3.** Rename, retag, archive, and explicit workspace move are metadata operations; they do not rewrite content revisions or change output identity. A source-session move does not move its previously saved outputs.

**ID-4.** Each saved revision describes the whole deliverable at that point, including a primary file and any supporting files. Removed files are absent from the next revision but retained in earlier intact revisions. Storage deduplication is an implementation option, not a user-visible dependency.

**ID-5.** Forking a Pi conversation does not fork outputs. New work creates a new output unless the user explicitly selected a revision target. No automatic ancestry-based overwrite permission is granted.

## 6. Output intent and framework contract

### 6.1 Policy and defaults

The output policy is separate from Parallel's execution destination. Enabling output behavior must not reroute prompts, start hidden workers, or change model selection.

| Policy | Selection | Required behavior |
| --- | --- | --- |
| Automatic | Default workspace preference; overridable per submission | Deck supplies output context/tools. Agent may publish intentional deliverables. No artifact is inferred merely from a finished message or a file appearing on disk. Missing publication is not automatically an error because output intent may be ambiguous. |
| Require output | Persistent workspace preference or explicit per-submission selection | Deck records an expected deliverable set before execution, defaulting to one slot. Each registered slot needs a committed revision or a visible incomplete/failure state. Saving files is not proof the user's substantive request is fulfilled. |
| Chat only | Persistent workspace preference or explicit per-submission selection | No agent output publication for that submission. Existing library contents remain unchanged. User-initiated Save as output and explicit attachment/reuse are still available. |

**INT-1.** The effective policy must be visible before sending. Per-submission overrides apply only to that submission; later submissions return to the workspace default. A preference change does not change already-running attempts.

**INT-2.** On first use, explain Automatic, the local folder, and how to choose Require output/Chat only. Do not require a separate setup wizard or a named workspace for ordinary use.

**INT-3.** Ordinary clarification questions, acknowledgments, progress, thinking, and raw tool activity are not deliverables under Automatic. The agent receives this policy automatically. No additional classification-model call is required.

**INT-4.** Save as output on a completed assistant answer must create a normal output from that user-selected text without regenerating it. The user can adjust its suggested title and include selected files. Existing history is not bulk-imported by default.

**INT-5.** Ordinary unbound submissions cannot append to an existing output merely because the agent guessed its ID/title. Explicit Revise binds an existing target. Agents may propose new outputs or refer to known inputs, but cannot rename, move, accept, trash, or overwrite arbitrary library entries.

**INT-6.** The expected deliverable set is visible on the attempt. The managed contract requires the agent to register distinct deliverables it identifies before saving them; users can correct the set, and explicit UI/workflow expectations are authoritative. Once registered, slots cannot be silently dropped by the agent; withdrawal is a user decision. Interpreting “three reports” from prose remains model-assisted, not a guaranteed host parser. Show what was actually registered/saved, and never claim the whole task is complete solely because one file exists. This does not require the user to supply paths, schemas, or another storage prompt.

### 6.2 Publication, not prompt-only compliance

**PUB-1.** Deck supplies the destination, output capability, metadata contract, and current policy through a managed runtime integration. The user never needs to prescribe folder layout, output IDs, JSON metadata, or save instructions in each task prompt.

**PUB-2.** The host owns identity, workspace membership, revision allocation, source attribution, path authorization, timestamps, file checksums, and commit acknowledgment. Agent-supplied titles, summaries, and content are untrusted inputs, not authoritative ownership or verification evidence.

**PUB-3.** A publication request must declare a deliverable's files and primary file. Deck validates the files and metadata, commits the package, and only then acknowledges Saved. A prose claim such as “I saved report.md” is not evidence of publication.

**PUB-4.** Publication is atomic per revision, not across unrelated outputs. Interrupted or failed multi-file writes never expose a half-saved revision as current. The previously committed revision remains usable. Bytes must be staged before the durable commit boundary is crossed.

**PUB-5.** Replaying the same publication request/receipt after transport retry or restart returns the same output/revision outcome, not another revision. Idempotency belongs to Deck, not model memory. Idempotency records must survive index deletion and be recoverable from durable output/attempt records.

**PUB-6.** A turn may intentionally save multiple independent outputs. Saved outputs survive a later agent failure or cancellation, labeled with the actual source outcome if known. Unsaved staging data is not promoted automatically. For Require output, the UI lists every registered slot and reports counts such as **2 saved · 1 still missing** or **2 saved · 1 save failed**. A successful first save cannot hide pending/failed slots or imply the entire user request was fulfilled.

**PUB-7.** At the actual end of the relevant work—not just an intermediate assistant/tool completion—Require output with no committed result shows **Finished without a saved output**. A partially saved deliverable set remains visibly incomplete; a failed save shows the concrete failure. The user can retry saving staged content, save a completed answer manually, ask for another attempt, or explicitly dismiss an expectation. Do not silently start an unlimited repair loop or incur another model call.

**PUB-8.** Session/run completion, output-save outcome, and human review are separate dimensions. Preserve existing runtime Completed/Failed semantics. Output cards display save/review problems independently; output objects do not become fake session rows in Work.

**PUB-9.** Draft sessions and resumed sessions receive the same contract. If the installed Pi runtime lacks the required managed integration, clearly report output publishing unavailable. Do not claim success or silently downgrade Require output to Automatic/Chat only. Ordinary chat and user-initiated Save as output must remain available.

### 6.3 Files created outside the library

Agent code may legitimately write source files or other working files. Those writes do not automatically become library outputs. A declared external file must be authorized and copied into a managed revision to become a durable output; a bare external path cannot be its only stored content. External links may be recorded as supporting references, not described as retained file bytes.

Selecting a file/output authorizes only that resource, not recursive indexing or publication of neighboring directories. All path checks occur in Electron main, not by trusting renderer/model-supplied strings.

## 7. Local storage, metadata, and recovery

### 7.1 File-based source of truth

**FS-1.** The product has one active local library root. The proposed default is `${PI_DECK_HOME:-~/.pideck}/outputs`; the user may select an empty local folder before first use. The folder must be discoverable through settings and Reveal in Finder. It is not inferred from project cwd.

**FS-2.** Nonempty-library relocation and multiple simultaneous libraries are deferred. If the root becomes missing, read-only, or unavailable, show Library unavailable and offer retry/recovery guidance. Never silently create a replacement empty library or report existing outputs as successfully deleted. Chat can continue; saving fails visibly.

**FS-3.** Committed content, revision manifests, output metadata, review notes/decisions, and necessary publication receipts must exist as ordinary local files with documented versioned schemas. The index may use a local database, but must contain no unique authoritative output/review state.

Illustrative layout; precise directory names are a technical-design choice:

```text
<library>/
  <readable-name>--<output-id>/
    output.json
    reviews.json
    revisions/
      <revision-id>/
        revision.json
        files/
          report.md
          supporting-data.csv
  .staging/                 # attempts, never indexed as saved outputs
  .trash/                   # explicitly deleted packages, not normal results
```

**FS-4.** A readable title/slug is presentation, not identity. Renaming a title need not rename physical directories. File references within a package must be relative and contained; paths must not depend on an original machine's absolute root.

Minimum durable metadata:

| Record | Required information |
| --- | --- |
| Output | Schema version, stable ID, owning workspace ID and display-name snapshot, title, optional summary/tags, content kind, created/updated time, current revision, archive state. |
| Revision | Schema version, output/revision IDs, display number, optional base revision, origin (`agent`, `manual-save`, `import`), creation time, primary file, relative file inventory with sizes/media types/content hashes, source provenance when available, publication identity/receipt. |
| Review | Output/revision IDs, user-authored notes and decision events with timestamps; no agent authority to set Accepted. |
| Attempt | Stable request ID, intended new-output/revision target, policy, expected head/root/workspace binding, state and committed receipt or recoverable failure. No private child payloads. |

**FS-5.** Do not persist raw parent prompts, private worker traces, credentials, attachment tokens, or hidden thinking merely to populate metadata. Provenance may retain safe user-facing session/workflow references; unavailable sources remain explicitly unavailable. Content itself is user-produced material and is not guaranteed secret-free.

**FS-6.** Opening, accepting, exporting, reusing, or revising an output must validate the selected revision's manifest/content integrity. A stale index is not permission to use changed or missing bytes silently.

### 7.2 Failure and rebuild behavior

| Condition | Required product behavior |
| --- | --- |
| Crash before revision commit | No Saved acknowledgment; prior revisions remain current. Recoverable staging is shown as interrupted, not published or searchable content. |
| Crash after commit, before acknowledgment/indexing | Recover the same committed revision/receipt. Show it once, and reconcile the index without asking the model to regenerate it. |
| Index lost/corrupt | Rebuild from valid committed packages. Preserve IDs, revisions, review state, archive/trash exclusion, and provenance without reading source sessions. |
| Revision file missing but manifest survives | Show Missing files and affected file names. Do not fabricate a complete/accepted preview or silently replace it with a different revision. |
| Entire output package removed externally | Remove its stale search hit after reconciliation and explain absence when a previous link is opened. An index cannot restore deleted files. |
| Metadata malformed/unsupported | Preserve files and show a recoverable package/schema error. Do not reset/delete packages or infer arbitrary files as trusted output records. |
| Duplicate output/revision IDs in copied packages | Flag identity conflict; do not silently merge or overwrite. Explicit import-as-new may allocate new identity. |
| Unknown workspace ID when recovering copied metadata | Show an unassigned recovery item and ask the user to map it to an existing/default workspace; do not grant agent access or create workspaces silently. |
| Oversized or unsupported content | Preserve only within publication limits; label preview/index limitations. Never claim complete search coverage when content was skipped. |

**FS-7.** Metadata operations and publication must be serialized or revision-fenced appropriately. Crashes, duplicate requests, and concurrent app operations must not leave a current pointer referencing a partial/nonexistent committed revision.

**FS-8.** Published history is immutable through Deck, not magically immutable on the filesystem. External programs can alter/delete bytes. Deck must detect this and never claim it can recover the original bytes without an intact stored copy or backup.

## 8. Review and revision behavior

### 8.1 Separate state dimensions

| Dimension | Values / meaning |
| --- | --- |
| Output availability | Available, missing/damaged, or library unavailable. |
| Publication attempt | Pending/preparing, saved, failed, interrupted, or revision conflict. Not a review verdict. |
| Revision review | Unreviewed, Changes requested, Accepted. New saved revisions always start Unreviewed. |
| Organization | Active, archived, or in Trash. Not evidence about content quality. |

**REV-1.** A saved result is immediately reviewable without declaring it “ready” in a prompt. No separate draft/approved workflow is required to find it. Failed or unfinished staging is not a saved revision.

**REV-2.** Review notes and decisions attach to a specific revision. Users can add notes, request changes with feedback, accept, or reopen review. Preserve decision history. A new revision never inherits Accepted from its predecessor.

**REV-3.** Accepted is a user decision about the selected intact snapshot, not a factual-quality badge, test result, permission grant, filesystem rollback, or external publication. Show agent-reported claims as such. Structured check execution/CI integration is not required in this release.

### 8.2 Iterating from an output

**REV-4.** Revise opens a lightweight new session draft in the output's owning workspace by default. It binds the selected revision, chosen files, and review feedback; it does not load the source transcript or start a worker until Send. A visible target chip shows the output title and revision. Users can instead attach a revision target to an existing compatible session explicitly.

**REV-5.** On send, Deck supplies the selected snapshot, output contract, authorized staging destination, and explicit target automatically. From the normal output detail, the default target is current. When Revise is invoked while viewing a specific historical revision, that selected revision remains the target and requires a visible base-version acknowledgment before Send; never silently substitute current. Finishing saves a new revision of the same output, not an unrelated library entry.

**REV-6.** Initial scope permits one revision target per submitted job. Other selected outputs are read-only inputs. Multiple-output editing/transactional batches are deferred.

**REV-7.** Publication checks the expected current revision and workspace ownership captured for the attempt. If another session has advanced the output, retain the candidate in recoverable staging and show **A newer revision exists**. Do not overwrite the newer revision, silently merge, or silently redirect to a new output. Offer review/retry from current or an explicit Save as separate output without regenerating the candidate.

**REV-8.** Publishing a new revision assigns a stable increasing display number. Previous revision IDs/numbers and references do not change. Repeated transport delivery of one attempt is not a new revision. A user-requested new iteration is a new attempt.

**REV-9.** Compare offers side-by-side/plain textual comparison for supported text files and an added/removed/changed file list. For unsupported binaries, show metadata differences and open/export actions; do not promise semantic diffs.

### 8.3 External edits

**REV-10.** Export a copy produces editable ordinary files without modifying the library. Import as revision requires explicit user selection, previews the target, copies bytes into managed storage, and applies the same expected-head/integrity checks as an agent revision. It makes no model call and preserves import provenance.

**REV-11.** A direct edit to a published file invalidates its integrity status. Mark it Externally modified, invalidate any “Accepted for current bytes” presentation, and suspend normal reuse/revision/acceptance of that snapshot until the user resolves it. Resolution actions such as inspect/export, adopt-as-new-revision, remove, or restore remain available. Historical acceptance remains a historical event, not approval of the changed bytes.

**REV-12.** The user may inspect/export changed files, explicitly adopt them as a new revision, or restore from an independently intact copy. Adoption does not falsify the old manifest or repair lost history: the affected old revision remains marked damaged if its original bytes are unavailable. No silent checksum update to preserve a false immutable-history claim.

## 9. Retrieval, preview, and reuse

### 9.1 Library navigation and search

**FIND-1.** Provide All Outputs across active workspaces and the same view scoped to a workspace. Keep Outputs distinct from Work: Work answers “what is running/needing intervention”; Outputs answers “what was produced.” Navigation between library, output detail, and source session preserves query/filter/selection context.

**FIND-2.** Each result shows title, type, workspace, current revision/review state, updated time, file count, a bounded summary/snippet, and any save/integrity/index limitation. Opening it shows primary content, supporting files, revision history, review actions, source links, and Reveal/Export actions.

**FIND-3.** Default search covers title, summary, tags, file names, and supported current-revision text. Match Unicode-normalized, case-insensitive query terms; all terms must match somewhere in the searchable output fields/content. No semantic relevance or fuzzy matching is promised. Filters intersect with the query.

**FIND-4.** Offer workspace, content kind/file type, current-review-state, updated-date, and archived filters. Default ordering is updated time descending, with stable output-ID tie-breaking. Title/file-name matches may be visibly distinguished, but must not depend on model-generated ranking.

**FIND-5.** Older revisions are not mixed into default result rows. Users can inspect/search supported text within a selected historical revision. Full cross-library historical-content search is deferred. The latest accepted revision is accessible in detail but never silently substitutes for current.

**FIND-6.** Search/index building is local and does not require provider authentication. The user can refresh/rebuild the index. Rebuild is resumable/cancellable, reports progress/partial coverage, and does not block opening known valid outputs. Newly committed outputs appear immediately by metadata with Indexing status until text becomes searchable.

**FIND-7.** External-change reconciliation runs on library open/refresh and before content-sensitive actions. Background file watching may improve freshness but is not the sole correctness mechanism. Missing/changed files must not remain silently trusted just because no watcher event arrived.

### 9.2 Preview and content bounds

Initial proposed safety limits, to be exercised by design/performance fixtures before implementation sign-off:

| Resource | First-release behavior |
| --- | --- |
| Publication | At most 100 regular files, 100 MiB per file, 250 MiB total per revision. Exceeding limits refuses publication atomically and preserves actionable staged work. |
| Full-text indexing | UTF-8 Markdown/plain text/JSON/CSV up to 2 MiB per file. Larger/unsupported files receive metadata/file-name search only, with a visible explanation. |
| Inline preview | Bounded text preview up to 256 KiB; clearly label truncation. CSV may use a table preview but must also respect bounded rows/bytes. |
| Other formats | Retain within publication limits; offer metadata, Reveal, and explicit OS open/export. Rich PDF/Office/HTML/SVG rendering and OCR are deferred. |

**VIEW-1.** Previews are non-executing and safely escaped/sanitized. Do not execute HTML, scripts, SVG, or embedded code; do not fetch remote Markdown images/resources automatically. External links require explicit user activation and the existing scheme allowlist.

**VIEW-2.** Binary detection, invalid text encodings, malformed JSON/CSV, and file-extension/content mismatches must produce honest fallbacks, not crashes or claims that full-text indexing succeeded. Content parsing/rendering is bounded; unsupported structured text may fall back to plain text when safe.

**VIEW-3.** Accessibility includes keyboard library/detail/revision navigation, labeled review actions, visible focus, non-color-only states, readable search snippets, and no focus stealing during indexing or publication updates.

### 9.3 Reusing results in new work

**USE-1.** Use in session opens an output picker or attaches the chosen revision as a clearly labeled input. The user sees selected files, revision, and size before sending. Pinning must protect content, not just IDs: on Send, Deck validates hashes and either snapshots the selected bytes into the attempt's inputs or validates every host-mediated read against the recorded hashes. If files change or disappear before delivery, fail the binding visibly instead of delivering changed bytes. The same rule applies to Revise. Later library revisions do not silently change in-flight inputs.

**USE-2.** Agents may use a host-scoped output lookup/read capability for the active workspace; only requested bounded results and authorized selected content are supplied. The entire library is never automatically injected into prompts. The UI can search globally, but cross-workspace reuse requires explicit user selection and grants read access to that pinned revision only.

**USE-3.** Revising an output from another workspace routes to a draft in the output's owning workspace, or requires an explicit authorized target binding there. A read-only cross-workspace attachment is not write permission. Model-supplied workspace IDs or paths cannot grant access.

**USE-4.** When original transcripts are missing, outputs remain usable. When selected output bytes are missing/changed, block silent substitution and let the user repair, remove, or deliberately select another revision. A stale output reference must never resolve to a different same-named file.

## 10. Organization, deletion, and disk use

**LIFE-1.** Users may rename, tag, explicitly move ownership, or archive an output. Archiving hides it from default results but does not remove content, history, or existing pinned references. Archived workspaces' outputs are excluded by default and discoverable through explicit archived filtering.

**LIFE-2.** Deleting/archiving/moving a source session never implicitly deletes or moves saved outputs. Workspace deletion/removal must explicitly preserve/reassign outputs or ask the user what to do; no cascading permanent content deletion. An output can outlive any execution source.

**LIFE-3.** Delete output requires confirmation describing all revisions and moves the complete package to library Trash. Trash is excluded from normal search and index rebuild. Restore preserves identity unless there is a collision, which requires user resolution. Permanent deletion is separate and confirmed. No automatic retention deletion in the first release.

**LIFE-4.** Deleting individual historical revisions is deferred. The first release manages whole-output Trash/restore to keep pinned references and numbering understandable. External deletion of an individual revision is handled as missing/damaged data, not a renumbering instruction.

**LIFE-5.** Moving, trashing, or permanently deleting an output with a pending revision attempt must not race publication. Block the operation with a clear active-attempt explanation or explicitly cancel/revoke the output attempt first. Revoking output authority does not imply killing the parent Pi process or undoing its other actions. Stale publications cannot resurrect a trashed output or write under its former ownership.

**LIFE-6.** Show output/library storage use, revision count, Trash size, and recoverable staging. Cleanup is explicit; deleting index/cache files never deletes authoritative content. Disk-full and permission failures retain the last committed state and explain why saving failed.

## 11. Sessions, Parallel, and workflows

### Ordinary and resumed sessions — initial release

- Apply the workspace policy through the managed integration, not modifications to project `AGENTS.md` or the user's global Pi configuration.
- Runtime bindings must be refreshed safely on resume/fork and never treated as durable output identity.
- A result card links to the exact committed revision; reopening it later must not silently open a newer revision without indicating the difference.
- Source session deletion leaves a non-navigable provenance record, not a missing output.

### Deck-managed Parallel — initial release, parent boundary only

- Preserve deterministic Parallel prompt routing and the existing private task-session contract.
- Output intent follows the originating user submission through planning and parent synthesis; overlapping submissions cannot satisfy one another's Require output expectations.
- Only the parent-facing finalization/publication boundary may commit library output. Private workers must not gain arbitrary library write/lookup capabilities or independent output rows.
- Initial file publication is limited to parent-created/parent-authorized content already available at that boundary. General promotion of arbitrary child file trees is deferred; do not expose child paths/transcripts to implement a shortcut.
- Parent synthesis text can become an output under the same policy. A child finishing does not satisfy the parent output expectation; private intermediate outputs are not automatically indexed.

### Agent Workflows — later 0.7.x slice

- Add an explicit **Save deliverable to Outputs** setting to selected user-visible Worker nodes; ordinary nodes and existing workflow definitions default to no library publication.
- This is configured once in the workflow definition and snapshotted with the run, not repeated in every run prompt. Decider/Human/Orchestrator internal values are not indiscriminately published.
- Each run saves new outputs by default. Appending to an existing output requires a separately explicit pinned target; no implicit overwrite by workflow/node name.
- Preserve canonical node roles, runtime ownership, run revisions, and existing output/input-binding semantics. Library publication failure is shown separately from node execution outcome, and retrying a save must not rerun the worker unnecessarily.
- A later workflow integration must define publication at safe graph boundaries, including fan-out/loops, before claiming full workflow coverage. Human-node routing remains its own existing runtime contract; accepting a library revision does not automatically answer a pending Human node.

## 12. Safety and integrity requirements

**SAFE-1.** Electron main owns all library filesystem operations and authorization. Renderer/model inputs are validated requests/opaque IDs, not arbitrary read/write paths. Verify actual containment and current ownership, not just string prefixes.

**SAFE-2.** Treat file manifests and copied packages as untrusted. Reject absolute/traversal paths, symlink escapes, non-regular file reads, invalid/duplicate relative file names, and unsafe publication targets. Do not follow arbitrary external links during rebuild/preview. Canonicalize and revalidate roots where required.

**SAFE-3.** Indexing/previews never execute stored content or shell commands and never invoke provider models. File extraction is bounded, cancellable, and isolated from normal UI responsiveness. Malformed packages cannot block the entire library indefinitely.

**SAFE-4.** Publication is a file-management boundary, not a security sandbox for Pi. Do not imply that an agent cannot access other filesystem locations through its ordinary tools. Do not silently edit or replace the user's installed extensions.

**SAFE-5.** No implicit external publication, synchronization, analytics upload, full-transcript export, hidden-reasoning capture, or private-child metadata leakage. Opening external applications is explicit. Diagnostics must avoid recording output bodies/secrets by default.

**SAFE-6.** Data migrations preserve files and identify unsupported newer schema versions. A schema/index error must never trigger destructive “reset library” behavior. Content integrity checks and current ownership must gate sensitive actions even if cached UI state is stale.

## 14. Success measures and validation

### Product acceptance through dogfooding

Before calling the first release successful, demonstrate with research, planning/writing, and structured-data tasks:

- Produce at least five useful outputs across at least two workspaces without putting directory layout, metadata schema, or save instructions into user prompts.
- Retrieve a chosen output by its content without opening the source conversation.
- Complete at least two review/revision cycles, including one after source-session deletion and one from a different session.
- Export an output and inspect its files/metadata outside Deck.
- Rebuild the index and recover the same meaningful library state.
- Ask the user whether the library replaced their current manual filing/retrieval habit. A file-count metric alone is insufficient.

Measure task time and friction during these exercises; do not claim a quantified productivity improvement without evidence. No hosted telemetry is necessary.

### Responsiveness targets

For a documented baseline Mac and a reproducible fixture of 1,000 outputs, 5,000 revisions, and approximately 50 MiB of searchable current text:

- Warm local search should target p95 under 300 ms.
- Metadata for a committed output should become visible without waiting for full-text indexing.
- Indexing/rebuild/import must show progress and remain cancellable without blocking chat, navigation, or known-output opening.

These are design/performance targets to measure, not flaky wall-clock assertions to add blindly to CI. Adjust the fixture/budgets explicitly if design evidence requires it.

### Authoritative correctness gate

- Add deterministic schema/store/publication/rebuild/revision/privacy tests and fake-RPC Electron E2E for the acceptance matrix.
- `npm run verify:ci` is the canonical CI contract. Wire new deterministic commands into it if they are not already covered by the existing suite.
- Implementation PRs require the protected **Verify desktop app** check on the current commit. Inspect uploaded Playwright screenshots/traces/reports on E2E failure; a retry alone is not evidence.
- Authenticated provider/model smoke remains release-only unless CI receives an explicitly safe credentialed environment. Validate automatic publication guidance with real supported models at release time without pretending deterministic fixtures prove model compliance.
- This document/issue creates no implementation or CI-pass claim. No runtime code changes are part of this planning task.

## 15. Delivery slices and design handoff

### Slice 0 — Resolve the safety-critical design

Before full UI implementation, demonstrate:

1. Versioned output/revision/review/attempt contract and a recoverable multi-file commit protocol.
2. Managed Pi integration that supplies policy, validates publication, and correlates output attempts with normal and Parallel parent turns across restart.
3. Revision-target bindings that cannot overwrite a newer head or survive revoked ownership accidentally.
4. Safe file access, external-change detection, rebuild, and bounded preview/index behavior.

This is a feasibility/design gate, not a production feature or license to expand scope. It should yield concrete examples and failure fixtures for the approved product contract.

### Slice 1 — Initial library release within 0.7.x

A coherent end-to-end release, not disconnected infrastructure. Its exact patch/date follows Slice 0 sizing; this is an intentionally substantial scope, not a promise that all adjacent UX fits a quick 0.7.0. If needed, move comparison/general-import UI polish to a named follow-up through product review, but do not cut publication integrity, recovery, pinned revisions, or the usable produce/find/review/revise loop:

- Ordinary/resumed parent sessions, Automatic/Require output/Chat only, manual save, and parent-boundary Parallel publication.
- Local packages, stable identities, atomic/idempotent save, revision retention, recovery, rebuildable metadata/text search.
- All/workspace Outputs, safe previews, review notes/decisions, contextual Revise, pinned reuse, compare for supported text.
- Export/import-as-revision, integrity warnings, explicit archive/Trash/restore, storage visibility, and accessibility.
- Acceptance A1–A16. Workflow automatic publication is not advertised yet.

Subdivide implementation into mergeable PRs as needed, but do not market the initial library as complete before users can produce, find, review, revise, and recover a result.

### Slice 2 — Workflow integration within 0.7.x

- Explicit configured deliverable boundaries on suitable Worker nodes.
- Run-snapshotted publication intent and safe per-run output identity.
- Idempotent publication recovery without accidental worker reruns.
- Acceptance A17 and concrete loop/fan-out design before expanding coverage.

### Later, only after dogfooding

Richer document previews, saved searches, cross-library historical search, library relocation/import UI, storage deduplication/pruning, richer evidence/check adapters, and optional Git-derived views. None is a prerequisite or rationale for weakening local-file durability.

### Decisions left to design, not ambiguities in product behavior

- Exact layout/navigation placement and control labels, while keeping policies and revision targets visible.
- Metadata field spelling/schema versions and publication transport, preserving the required semantics.
- Local index technology; no hosted/provider dependency and no authoritative index-only data.
- Supported Pi version/capability detection and extension lifecycle integration.
- Concrete recovery/reconciliation algorithms and accessibility interaction details.
- Measured preview/index/storage limits, with explicit review of any change to the proposed budgets.

Require a product amendment before introducing Git as a dependency, storing the only authoritative copy in a database, capturing private child internals, auto-accepting revisions, replacing source bytes silently, or requiring repeated storage prompts.
