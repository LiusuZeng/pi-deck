# Backend pending items

- [x] **Preserve reopenable Pi sessions for completed Agent Workflow occurrences.** **Verified:** workflow occurrence records retain a historical `runtimeId` after the scheduler closes and unregisters that runtime at terminal completion; the previous-runs UI then attempts to open that detached runtime and can show “Chat runtime is no longer attached.” A workflow occurrence must retain its durable `sessionFile`/session identity and reopen that individual Pi session unless the user explicitly deletes or archives it. **Plan:** (1) define `runtimeId` as live-only and `sessionFile` as the durable reopen reference; (2) persist/validate the durable reference for every workflow-created session and retain it after terminal closure and rehydration; (3) have terminal occurrences resume from `sessionFile` directly, reserving `runtimeId` lookup for running occurrences; (4) provide a clear unavailable/deleted-session message only when the durable session is genuinely absent, unreadable, or explicitly archived/deleted; (5) add backend lifecycle and renderer/real-Pi integration coverage for completed, failed, restarted, and explicitly deleted/archived sessions. Decide separately whether resumed workflow sessions accept follow-up prompts; opening and viewing the session is required regardless.

- [ ] **[Render configured workflows and live runs as a real execution graph](workflow-live-execution-graph-design.md).** Replace the read-only text-and-arrows representation with one canonical, accessible graph of role nodes and directed connections. Reuse the same graph layout and node/edge semantics for the static configured-workflow view and the run view; the latter overlays current occurrence state so users can immediately distinguish not-started, queued/waiting, in-progress, completed, failed, skipped, cancelled, retrying, and waiting-for-human work. **Plan:** (1) inventory the canonical workflow graph contract (node IDs, transitions, branch/loop/fan-out semantics) and occurrence/run state already persisted by the engine; define any missing stable node-to-occurrence mapping, attempt/iteration, timestamps, error, and active-human-gate summary fields without exposing raw session content; (2) specify a versioned renderer-facing graph snapshot/subscription contract, including initial load, run updates, restart/rehydration, terminal states, and authorization/redaction boundaries; (3) build a shared graph model/layout layer that produces deterministic node positions and edge routing from the workflow definition, with responsive, keyboard-accessible node selection and a non-visual textual equivalent; (4) implement the static read-only graph first, then overlay live run status, progress, retries, fan-out, and loop iterations in the run view without changing execution semantics; (5) define node-detail drill-in for concise status/output summaries, human actions, and the existing explicit Pi-session deep link; (6) add schema/store/scheduler tests for graph snapshot accuracy and update ordering, renderer tests for every state and accessibility, and real-Pi/E2E coverage for a multi-node run, fan-out/loop, retry/failure, waiting-human, restart recovery, and terminal runs.

- [ ] **Add explicit workflow-node input-source configuration.** The current canonical runtime implicitly passes only immediate parent occurrence output to a connected successor; users need to explicitly choose which earlier node outputs feed a node (for example, step 4 consuming steps 1, 2, and 3), while retaining the simple default for ordinary sequential connections. **Plan:** (1) write a versioned canonical JSON contract for input bindings that identifies a source node, the source value (`finalOutput` initially), and an optional bounded presentation label; define defaults so existing relationships preserve immediate-predecessor handoff without migration breakage; (2) define graph/role validation: source IDs must exist and be reachable before the target, bindings must not cross illegal orchestrator ownership boundaries, conditional/fan-out sources need deterministic aggregation/selection rules, and output-less/human/terminal sources are rejected or explicitly supported; (3) decide first-version semantics for multiple bindings—stable source order, bounded per-source output, clear labels, and no expression language, arbitrary field paths, or implicit transcript inclusion; (4) evolve occurrence lineage/context and prompt rendering so each target resolves its declared bindings from the immutable run snapshot, including correct loop iteration and fan-out occurrence selection, then persists the exact resolved/bounded handoff context for reproducibility and restart recovery; (5) expose a compact builder control and read-only graph annotations that show every configured input source, with an accessible textual equivalent and clear validation errors; (6) preserve legacy explicit `stepOutput` behavior and migrate/import only when semantics are unambiguous; (7) add schema, validator, store migration, runtime, prompt-renderer, renderer, and E2E coverage for linear multi-source handoff, decisions, fan-out, loops, retries, missing/failed sources, cancellation, and restart recovery. Completion requires users to be able to inspect exactly what sources a node will receive and a completed run to reproduce that resolved context without depending on process memory.

- [ ] **[Use stable opaque IDs—not agent names—for workflow nodes and references](workflow-node-identity-design.md).** Agent/node names are mutable display labels and must never identify a node in relationships, orchestrator ownership, input bindings, occurrence lineage, graph selection, or persisted runtime state; duplicate names must be allowed. Internal cross-workflow identity is `(workflowId, nodeId)`; `revision` and timestamps remain metadata, not identity. A short ID may be display-only but never a persisted lookup key. **Plan:** (1) implement the linked identity contract; (2) audit and remove name-keyed references across schemas, runtime, persistence, IPC, graph, and renderer; (3) migrate safely and preserve historical run snapshots; (4) validate duplicate-name, rename, rehydration, and historical-run behavior as specified in the linked design. The detailed delivery sequence, migration rules, and completion gate are in that design document.
