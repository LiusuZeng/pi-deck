# Pi Deck v0.6.0 — Review Feedback

**Target branch:** `feature/v0.6-unified-work`  
**Review status:** **Changes requested after UX / battlefield audit**  
**Updated:** 2026-08-23 after real UI use exposed an internal-session leak  
**Previously validated product candidate:** `80ddc035871a2c9cd91e34ab8b78f449c3b6b52a`

## Current verdict

The original architectural review findings were addressed successfully: Unified Work is coherent, the branch contains the current `v0.5.5` baseline, Work is a primary surface, and default-workspace mechanics are progressively disclosed.

A subsequent real-UI audit exposed one concrete behavior bug that violates an existing Parallel Task Sessions contract: an internal **`Task-session synthesis...`** session appeared as a normal top-level session in the sidebar.

That finding changes the release verdict from approved back to **changes requested** until the leak is fixed and regression-tested.

This is **not** a request to redesign Unified Work. It is a privacy/navigation boundary bug plus a small set of UX hardening items discovered while auditing the integrated experience.

# Open findings

## P1 — Private task-session synthesis leaks into normal session navigation

### Observed behavior

During real UI use, the normal session sidebar contained a top-level row whose title began:

```text
Task-session synthesis...
```

The row appeared alongside ordinary user-created Pi sessions and was navigable as if it were a normal session.

### Why this is a release blocker

The Parallel Task Sessions contract explicitly says that private task sessions are parent-owned implementation details:

- task sessions appear only in the dedicated task panel inside the parent conversation;
- users cannot open them as independent conversations;
- task sessions must not appear in the session sidebar, All Work, or scoped Work;
- planner/task workers are expected to use private / `--no-session` semantics and never enter normal session navigation.

A synthesis worker belongs to the same private execution boundary. A `Task-session synthesis...` row in ordinary navigation means an internal worker or session artifact has escaped into the user-facing session model.

This is more than cosmetic naming leakage. It can expose implementation lifecycle artifacts, pollute Work/session counts, create confusing resumable entries, and undermine the invariant that the parent session is the sole user-facing surface for Parallel children.

### Required investigation

Trace the synthesis lifecycle end-to-end. Do **not** fix this only by filtering titles that begin with `Task-session synthesis`.

Inspect at least:

- synthesis worker creation in the main-process Parallel integration;
- planner/task/synthesis Pi process arguments and whether every private worker uses the intended no-session behavior;
- any helper shared between parent workers and synthesis workers that may accidentally enable persistence;
- Pi JSONL/session-file creation during synthesis;
- normal `listSessions` / workspace hydration / sidebar discovery paths;
- Unified Work projection paths, to ensure an internal artifact cannot enter All Work or workspace Work;
- restart behavior after a synthesis run;
- cleanup behavior for any already-created leaked artifact.

The preferred fix is to prevent private synthesis workers from creating discoverable user-session artifacts in the first place.

A defense-in-depth discovery filter is reasonable only if private/internal identity can be determined structurally. Avoid relying on generated title text as the durable discriminator.

### Existing leaked artifacts

If the current implementation has already written synthesis JSONL/session files, fixing future worker creation may not remove rows already present on a developer/user machine.

The fix should explicitly decide what happens to pre-existing leaked artifacts:

- if they can be identified safely by durable metadata, exclude or clean them up;
- if they cannot be distinguished reliably from real sessions, do not delete user data heuristically; document the limitation and provide a safe cleanup path.

### Regression coverage

Add deterministic and authenticated real-Pi coverage that exercises the complete path:

```text
parent session
  -> Parallel prompt
  -> planner/private tasks
  -> synthesis
  -> synthesized result in parent
```

Then assert:

- [ ] no planner session appears in normal session discovery;
- [ ] no task worker appears in the sidebar;
- [ ] no synthesis worker appears in the sidebar;
- [ ] none of those workers appear in All Work;
- [ ] none appear in scoped Work;
- [ ] the only durable user-facing conversation is the parent session;
- [ ] restarting Pi Deck after synthesis does not reveal an internal session;
- [ ] existing parent/task-panel behavior still works.

### Acceptance criteria

- [ ] Reproduction no longer creates a `Task-session synthesis...` top-level session.
- [ ] Root cause is fixed rather than hidden by title-prefix filtering.
- [ ] Private planner/task/synthesis workers stay outside normal session persistence/navigation.
- [ ] Sidebar, All Work, and workspace Work all preserve the same private-session exclusion invariant.
- [ ] Regression tests cover both immediate UI state and restart/session rediscovery.

## P2 — Preserve Work filter state across Session drill-in / Back

### Current UX concern

`ActivityInbox` currently owns its selected status filter with component-local state:

```ts
const [selectedFilter, setSelectedFilter] = useState<ActivityFilter>("all");
```

Work and Session are separate primary surfaces. When Work unmounts during drill-in and is recreated on Back, component-local filter state can reset to `All`.

For heavy triage this creates repeated friction:

```text
All Work
  -> Needs attention
  -> open item
  -> inspect / respond
  -> Back
  -> filter has reset
  -> choose Needs attention again
```

The v0.6 navigation contract already preserves **scope origin**. It should also preserve enough transient Work-view context that Back feels like returning to the same place, not reopening Work from scratch.

### Recommended behavior

Preserve the selected status filter for the current renderer/navigation lifetime.

This does **not** require persistent settings or migration. Reasonable implementations include:

- include transient Work filter state in the Work origin/view state; or
- keep per-scope Work UI state at `App` level and pass it into `ActivityInbox`.

Avoid adding a new persistence schema merely for this.

### Acceptance criteria

- [ ] All Work → `Needs attention` → Session → Back returns to All Work with `Needs attention` still selected.
- [ ] Workspace Work → any status filter → Session → Back restores the same workspace and status filter.
- [ ] Explicitly switching to another Work scope may use that scope's own prior/default filter behavior, but it should be deterministic.
- [ ] Relaunch persistence is not required for v0.6 unless already available naturally.

## P2 — Restore triage position/focus when returning from a Work row

This is a UX-hardening recommendation rather than a release blocker.

Once Work becomes the primary triage surface, users will repeatedly open a row and return. Back should ideally restore context to the row that launched the Session.

Recommended behavior:

- remember the originating Work item identity while drilling into Session;
- on Back, if the item still exists under the active scope/filter, restore keyboard focus to that row and keep it visible;
- if the item moved category/disappeared because its status changed, fall back to the Work heading or nearest sensible location rather than leaving focus ambiguous.

Do not freeze Work ordering merely to preserve position; live status changes should still update normally.

### Acceptance criteria

- [ ] Keyboard users can open a Work row, Back, and continue triage without restarting from the top.
- [ ] Mouse users do not experience an unnecessary scroll jump when the originating item still exists.
- [ ] Status changes while inside Session degrade gracefully when the original row is no longer present.

# Architecture invariants — keep these locked

The new findings should be fixed without reopening the successful v0.6 product model.

## Work model

```text
Session/runtime state
        ↓
renderer-derived Work projection
        ↓
scope/status filtering
```

Do not introduce a persisted `WorkItem` entity as a bug-fix shortcut.

## Scope model

```text
All Work
  = Work(scope = all)

Workspace Work
  = Work(scope = workspaceId)
```

They remain the same conceptual surface with different scope.

## Navigation model

```text
All Work
  -> Session(origin = All Work)
  -> Back
  -> All Work

Workspace A Work
  -> Session(origin = Workspace A)
  -> Back
  -> Workspace A Work
```

The P2 filter/focus feedback extends this contract with transient **view context**; it does not change the underlying model.

## Workspace ownership

- Every user-facing parent session belongs to exactly one workspace.
- Global creation uses the stable default workspace internally.
- Workspace-scoped creation uses the selected workspace.
- Workspace membership is not inferred from filesystem path.
- Navigation must not mutate ownership.
- Hidden/background parent runtimes must not terminate merely because scope changes.

## Private Parallel boundary

- Planner/task/synthesis workers are private implementation workers.
- The parent is the sole normal conversation/navigation surface for Parallel children.
- Private workers must not become top-level sidebar sessions.
- Private workers must not appear in All Work or workspace Work.
- The renderer should not gain direct private-runtime navigation as a workaround.

## Saved-session identity

Preserve canonical user-session identity using workspace ownership plus `sessionFile`, durable Pi `sessionId` where available, and active `runtimeId` when attached.

Known saved-session navigation must not enter New Session / folder-picker behavior.

## Async navigation

Preserve navigation-generation / stale-transaction guards. Older asynchronous operations must not overwrite newer user navigation.

Once the open P1 issue is fixed, keep the previous recommendation:

```text
v0.6.0
  ↓
heavy real-work dogfooding
  ↓
v0.6.1 / .2 / .3 reliability + UX fixes
  ↓
then decide v0.7 from observed friction
```

Prioritize:

1. blocker — requires terminal fallback/restart
2. workflow break — significantly interrupts work
3. friction — repeated annoyance but work continues
4. cosmetic / nice-to-have

Do not immediately perform a broad `App.tsx` refactor simply because the integrated renderer is large. Let repeated real bugs reveal the stable seams worth extracting.

# Review conclusion

Unified Work still does **not** need another design pass.

However, the real UI observation of `Task-session synthesis...` in ordinary session navigation is a concrete violation of an already-defined product boundary and should be fixed before calling the v0.6 candidate release-ready.

**Current review verdict: CHANGES REQUESTED — fix private synthesis-session leakage, then rerun release validation.**

The filter/focus items are UX-hardening work that can be included before 0.6.0 if low-risk, or handled immediately in 0.6.x based on dogfood priority.
