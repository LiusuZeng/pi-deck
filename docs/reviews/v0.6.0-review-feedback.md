# Architecture invariants — keep these locked for v0.6.x

These contracts are now part of the successful v0.6 shape and should not be casually reopened while dogfooding fixes land.

## Work model

```text
Session/runtime state
        ↓
renderer-derived Work projection
        ↓
scope/status filtering
```

Do not introduce a persisted `WorkItem` entity as a bug-fix shortcut.

## Scope model

```text
All Work
  = Work(scope = all)

Workspace Work
  = Work(scope = workspaceId)
```

They are the same conceptual surface with different scope.

## Navigation model

```text
All Work
  -> Session(origin = All Work)
  -> Back
  -> All Work

Workspace A Work
  -> Session(origin = Workspace A)
  -> Back
  -> Workspace A Work
```

## Workspace ownership

- Every session belongs to exactly one workspace.
- Global creation uses the stable default workspace internally.
- Workspace-scoped creation uses the selected workspace.
- Workspace membership is not inferred from filesystem path.
- Navigation must not mutate ownership.
- Hidden/background runtimes must not be terminated merely because scope changes.

## Saved-session identity

Preserve canonical saved-session identity using workspace ownership plus `sessionFile`, durable Pi `sessionId` where available, and active `runtimeId` when attached.

Known saved-session navigation must not enter New Session / folder-picker behavior.

## Async navigation

Preserve navigation-generation / stale-transaction guards. Older asynchronous operations must not overwrite newer user navigation.

## Agent Workflows / Parallel task sessions

Unified Work does not turn either system into ordinary persisted Work entities. Preserve their existing boundaries unless a later product decision explicitly changes them.

### Merge-strategy implication

If the final PR is merged with a normal merge or fast-forward that preserves the validated tree, the validation evidence remains meaningful.

If GitHub uses **squash merge** or **rebase merge**, the resulting commit SHA will change. That is not inherently wrong, but the release process should then either:

1. rerun `npm run verify:release` against the exact final `main` / release tag, or
2. explicitly verify that the final release tree is identical to the validated product tree and record that fact.

For a milestone release, rerunning the release gate on the exact tagged commit is the clearest option.

# Post-release feedback — do not block v0.6.0

## 1. Enter feature-freeze / dogfood mode first

Do not immediately turn the successful v0.6 integration into another large feature branch.

Recommended mode:

```text
v0.6.0
  ↓
heavy real-work dogfooding
  ↓
v0.6.1 / .2 / .3 reliability fixes
  ↓
only then decide what v0.7 actually needs
```

Prioritize bugs according to real workflow impact:

1. blocker — requires terminal fallback/restart
2. workflow break — significantly interrupts work
3. friction — repeated annoyance but work continues
4. cosmetic / nice-to-have

The purpose of v0.6.x should be to establish a daily-driver reliability baseline rather than to expand the feature surface.

## 2. Do not refactor `App.tsx` just because v0.6 made it larger

The renderer still concentrates a large amount of session, workspace, navigation, workflow, and lifecycle coordination in `App.tsx`.

That is a legitimate maintainability concern, but **it is not a reason to delay v0.6.0 or immediately perform a broad architectural refactor**.

A large refactor immediately after a milestone integration would create fresh lifecycle risk before real usage has shown where the actual boundaries hurt.

Instead:

- dogfood first
- observe which bug clusters repeatedly involve the same responsibilities
- extract boundaries only when evidence shows a stable seam
- keep behavior-preserving refactors separate from new product behavior

Potential future extraction candidates may include navigation transactions, workspace/session loading, and runtime reconciliation, but no extraction is recommended merely to reduce line count.

## 3. Let battlefield telemetry determine v0.7

Do not assume the next feature based on roadmap aesthetics.

Examples:

- if real usage exposes lifecycle/resume bugs → keep hardening
- if the dominant friction is “I cannot tell what the agent is doing” → semantic progress/attention quality becomes a strong v0.7 candidate
- if terminal/editor handoff is the repeated problem → integration hooks become more justified

The preferred rule remains:

> **Build from friction, not imagination.**
